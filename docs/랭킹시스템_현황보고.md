## ① 랭킹 점수 기준

K-OSP 플랫폼의 랭킹은 **시즌 랭킹**과 **GitHub 전체 랭킹** 두 가지로 구성됩니다.

---

### 1-1. 시즌 랭킹 (최대 100점)

시즌(학기) 단위로 산정되며, 아래 5개 카테고리 점수의 합으로 결정됩니다.

#### 총점 계산식

```
총점 = min( 출석점수 + min(커밋점수 + 챌린지점수, 35) + 프로젝트점수 + 커뮤니티점수, 100 )
```

> 커밋·챌린지 합산 상한 35점, 전체 상한 100점

#### 카테고리별 점수 구성 요약

| 카테고리 | 이론상 최대 | 방식 |
|---------|-----------|------|
| 출석 기본 | ~1.8점 (180일 기준) | 자동 |
| 스트릭 보너스 | 19점 (전부 달성 시) | 자동 |
| 커밋 + 챌린지 | 35점 | 자동 |
| 프로젝트 | 30점 | 관리자 지급 |
| 커뮤니티 | 10점 | 자동 |

---

#### (1) 출석 점수

| 항목 | 점수 | 조건 |
|------|------|------|
| 기본 출석 | 0.01점 / 일 | 플랫폼 로그인 시 자동 부여 |
| 스트릭 보너스 (7일) | 1.0점 | 7일 연속 로그인 달성 시 일회성 지급 |
| 스트릭 보너스 (30일) | 3.0점 | 30일 연속 로그인 달성 시 일회성 지급 |
| 스트릭 보너스 (50일) | 5.0점 | 50일 연속 로그인 달성 시 일회성 지급 |
| 스트릭 보너스 (100일) | 10.0점 | 100일 연속 로그인 달성 시 일회성 지급 |

- 기본 출석 점수는 별도 상한 없음
- 스트릭 보너스는 해당 일수 도달 시 단 1회만 지급

---

#### (2) 커밋 점수 (커밋·챌린지 합산 최대 35점)

| 항목 | 점수 | 조건 |
|------|------|------|
| GitHub 커밋 | 0.05점 / 건 | 일별 최대 3건까지 인정 |

- GitHub에 연동된 커밋 기준으로 매일 04:00에 재계산
- 봇 커밋(메시지가 `[bot]`, `chore: bump`, `ci:` 로 시작하는 커밋)은 제외
- 커밋 점수와 챌린지 점수의 **합산 상한은 35점**

---

#### (3) 챌린지 점수 (커밋·챌린지 합산 최대 35점)

챌린지는 티어(난이도) 1~10단계로 구성되며, 달성 시 해당 티어 단가만큼 점수가 지급됩니다.

| 챌린지 티어 | 점수 / 건 |
|------------|----------|
| Tier 1 | 0.25점 |
| Tier 2 | 0.40점 |
| Tier 3 | 0.55점 |
| Tier 4 | 0.70점 |
| Tier 5 | 0.90점 |
| Tier 6 | 1.10점 |
| Tier 7 | 1.40점 |
| Tier 8 | 1.80점 |
| Tier 9 | 2.30점 |
| Tier 10 | 2.80점 |

- 챌린지 달성 건수 × 해당 티어 단가의 합산으로 계산
- 커밋 점수와의 **합산 상한은 35점**
- 매일 04:00 배치에서 재계산

**챌린지 등록 방법 (관리자)**

관리자 페이지(`/admin/challenges/create`)에서 UI를 통해 직접 등록합니다.

| 입력 항목 | 내용 |
|---------|------|
| 이름·설명 | 챌린지 명칭 및 상세 설명 |
| 티어 | 1~10 중 선택 (난이도 기준) |
| SpEL 조건식 | GitHub 통계 기반 달성 조건 수식 |

**SpEL 조건식이란?**

챌린지 달성 여부를 판단하는 수식으로, GitHub 활동 통계를 변수로 활용합니다. 수식의 결과가 **100 이상**이면 달성으로 판정됩니다.

사용 가능한 주요 변수: `totalCommits`(커밋 수), `totalPrs`(PR 수), `totalIssues`(이슈 수), `totalStarsReceived`(받은 스타 수), `contributedReposCount`(기여 저장소 수) 등

조건식 예시:
```
// 커밋 100회 달성
T(Math).min(totalCommits * 100 / 100, 100)

// PR 10개 달성
T(Math).min(totalPrs * 100 / 10, 100)

// 커밋 50회 + PR 5개 복합 조건
(T(Math).min(totalCommits * 100 / 50, 100) + T(Math).min(totalPrs * 100 / 5, 100)) / 2
```

**달성 평가 흐름**

매일 04:00 수확기(Harvester)가 GitHub 데이터를 수집한 뒤, 각 사용자의 미달성 챌린지를 조건식으로 자동 평가하여 달성 시 점수를 즉시 지급합니다.

**현재 구조의 제약 및 개선 계획**

현재 SpEL 평가 엔진에는 GitHub 전체 누적 통계(`GithubUserStatistics`)만 변수로 주입되어 있어, 아래와 같은 제약이 존재합니다.

- 시즌 시작 이전 GitHub 활동도 함께 집계되어 기존 활동이 많은 사용자가 첫날 즉시 달성 가능
- 출석 연속일수·달성 챌린지 수·게시글 수 등 플랫폼 내 활동 데이터는 조건으로 사용 불가

이를 해결하기 위해 `ChallengeEvaluator`의 SpEL 컨텍스트를 확장할 예정입니다. 확장 후 사용 가능한 변수는 아래와 같습니다.

| 변수 | 내용 | 현재 |
|------|------|------|
| `totalCommits` 등 | GitHub 전체 누적 통계 | ✅ 사용 가능 |
| `seasonCommits` | 현재 시즌 시작일 이후 커밋 수 | ⚙️ 추가 예정 |
| `loginStreakDays` | 현재 연속 로그인 일수 | ⚙️ 추가 예정 |
| `completedChallengeCount` | 달성한 챌린지 수 | ⚙️ 추가 예정 |
| `articleCount` | 작성한 게시글 수 | ⚙️ 추가 예정 |
| `teamJoinCount` | 팀 참여 횟수 | ⚙️ 추가 예정 |

확장 완료 시 기존 배지·칭호 시스템에서 사용 중인 달성 조건(커밋 수, 스트릭, 챌린지 달성 수, 게시글 수 등)을 챌린지에도 그대로 재활용할 수 있습니다.

#### (4) 프로젝트 점수 (최대 30점)

| 항목 | 점수 | 조건 |
|------|------|------|
| Level 1 프로젝트 기본점수 | 2.0점 | 관리자가 프로젝트 종료 처리 시 일괄 지급 |
| Level 2 프로젝트 기본점수 | 4.0점 | 〃 |
| Level 3 프로젝트 기본점수 | 6.0점 | 〃 |
| Level 4 프로젝트 기본점수 | 8.0점 | 〃 |
| Level 5 프로젝트 기본점수 | 10.0점 | 〃 |
| 팀장(Team Lead) 보너스 | +2.0점 | 역할이 팀장인 경우 추가 |
| PM 보너스 | +1.0점 | 역할이 PM인 경우 추가 |
| 팀원(Member) 보너스 | +0.0점 | 추가 없음 |

- 점수 = 레벨별 기본점수 + 역할 보너스
- 예시: Level 3 프로젝트에서 팀장 역할 → 6.0 + 2.0 = **8.0점**
- 프로젝트 종료 시 관리자가 일괄 지급하며, 전체 상한은 **30점**

**프로젝트 등록 및 점수 지급 절차 (관리자)**

현재 관리자 전용 UI 페이지가 미구현 상태로, 아래 API를 직접 호출하여 처리합니다.

| 단계 | API | 내용 |
|------|-----|------|
| 1단계 | `POST /v1/admin/seasons/{seasonId}/projects` | 프로젝트 생성 (이름, 레벨 1~5 입력) |
| 2단계 | `POST /v1/admin/seasons/projects/{projectId}/members` | 멤버 추가 (유저 ID, 역할 지정) |
| 3단계 | `POST /v1/admin/seasons/projects/{projectId}/close` | 프로젝트 종료 → 전 멤버 점수 자동 일괄 지급 |

- 역할(Role)은 `TEAM_LEAD`, `PM`, `MEMBER` 중 선택
- 종료 처리 시 미지급 멤버에게만 지급되므로 중복 지급 없음

### 1-2. GitHub 전체 랭킹 (최대 9점)

GitHub 계정의 **전체 활동 기간** 기준으로 산정하는 별도 랭킹입니다.

#### 총점 계산식

```
총점 = 활동 수준 점수 (0~3점) + 다양성 점수 (0~1점) + 영향력 점수 (0~5점)
```

---

#### (1) 활동 수준 점수 (최대 3점)

| 점수 | 조건 |
|------|------|
| 3점 | 커밋 100건 이상 **AND** PR 20건 이상 |
| 2점 | 커밋 30건 이상 **AND** PR 5건 이상 |
| 1점 | 커밋 5건 이상 **OR** PR 1건 이상 |
| 0점 | 해당 없음 |

---

#### (2) 다양성 점수 (최대 1점)

| 점수 | 조건 |
|------|------|
| 1.0점 | 기여한 저장소 10개 이상 |
| 0.7점 | 기여한 저장소 5~9개 |
| 0.4점 | 기여한 저장소 2~4개 |
| 0.0점 | 기여한 저장소 1개 이하 |

---

#### (3) 영향력 점수 (최대 5점)

| 항목 | 점수 | 조건 |
|------|------|------|
| 고스타 저장소 보유 | +2.0점 | 내 소유 저장소 중 스타 100개 이상 |
| 유명 저장소 PR 기여 | +1.5점 | 스타 1,000개 이상 저장소에 PR 머지 |
| 이슈 해결 기여 | +1.0점 | 머지된 PR로 이슈 10개 이상 종료 |
| 크로스 저장소 PR | +0.5점 | 타인 소유 저장소에 PR 머지 |

- 4개 항목이 조건 충족 시 각각 합산되며, 전체 상한은 5점

## ③ 개발 과정 애로사항 및 지원 필요사항

### 3-1. 개발 과정 애로사항

#### (1) GitHub API Rate Limit 문제

**Rate Limit이란?**

GitHub GraphQL API는 인증된 토큰 1개당 **시간당 최대 5,000 포인트**까지만 요청을 허용합니다. 여기서 포인트는 단순 호출 횟수가 아니라, 요청한 데이터의 양(노드 수)에 비례해 소모됩니다. 예를 들어 커밋 100건을 한 번에 가져오면 100 포인트, 저장소 목록 50개를 요청하면 50 포인트가 소모되는 방식입니다.

**5,000 포인트가 실제로 어느 정도 양인지**

활동이 많은 사용자 1명의 전체 데이터(저장소 목록 + 커밋 이력 + PR + 이슈)를 수집하면 요청당 수십~수백 포인트가 소모됩니다. 커밋 이력이 1,000건인 사용자의 경우 페이지 단위로 나눠 요청하더라도 커밋 수집에만 약 1,000 포인트가 사용됩니다. 즉, **활동이 풍부한 사용자 3~5명의 데이터를 수집하는 것만으로도 5,000 포인트 한도에 근접**할 수 있습니다.

**플랫폼에서 발생하는 문제**

K-OSP의 수확기(Harvester)는 매일 04:00에 전체 사용자의 GitHub 데이터를 일괄 수집합니다. 사용자가 수십 명만 넘어도 플랫폼 공용 토큰 1개로는 1시간 안에 전체 수집을 완료하기 어렵습니다.

**현재 대응 방법**

K-OSP는 회원가입 시 GitHub OAuth 연동이 필수이므로, 모든 사용자의 GitHub OAuth 토큰이 가입 시점에 암호화되어 DB에 저장됩니다. 수확기는 각 사용자의 데이터를 수집할 때 해당 사용자 본인의 토큰으로 요청하여, 토큰이 사용자 수만큼 분산되는 효과를 얻고 있습니다.

**남아 있는 위험 요소**

로그인 방식이 GitHub 로그인과 이메일·비밀번호 로그인 두 가지이기 때문에, 토큰 갱신 여부가 로그인 방식에 따라 달라집니다.

| 로그인 방식 | 토큰 갱신 | 위험 |
|-----------|---------|------|
| GitHub 로그인 | 로그인할 때마다 자동 갱신 | 낮음 |
| 이메일 로그인 | 갱신 안 됨 (가입 시 저장된 토큰 유지) | 만료 위험 있음 |

이메일로만 로그인하는 사용자는 최초 가입 시 저장된 토큰이 갱신되지 않아 시간이 지남에 따라 만료되거나, 사용자가 GitHub에서 앱 권한을 직접 취소할 경우 토큰이 무효화됩니다. 이 경우 해당 사용자의 GitHub 데이터 수집이 실패하고 플랫폼 공용 토큰으로 부하가 집중될 수 있습니다. 사용자 수가 증가할수록 이 문제가 심화될 수 있으며, 장기적으로는 GitHub App 등록이나 추가 OAuth App을 통한 토큰 풀 확보가 필요할 수 있습니다.

#### (2) 챌린지 조건 설계의 복잡성

챌린지의 달성 조건은 SpEL(Spring Expression Language) 표현식으로 저장되어 유연하게 설계하였으나, 챌린지 조건 항목 자체를 설계하고 검증하는 과정에서 많은 공수가 소요되었습니다. 특히 GitHub 활동 데이터와 플랫폼 내 활동 데이터를 함께 참조하는 복합 조건의 경우 검증에 어려움이 있었습니다.

#### (3) 프로젝트 관리자 UI 미구현

프로젝트 생성·멤버 등록·종료 처리 등 프로젝트 점수 지급에 필요한 백엔드 API는 모두 완성되어 있으나, 관리자가 이를 직접 사용할 수 있는 프론트엔드 관리 페이지가 현재 구현되지 않은 상태입니다. 현재는 API를 직접 호출하는 방식으로 운영하고 있으며, 관리자 UI 개발이 추가로 필요합니다.

#### (4) 비동기 점수 지급과 일관성 유지

출석·커뮤니티 점수는 이벤트 발생 즉시 지급(실시간), 커밋·챌린지 점수는 배치(매일 04:00)로 재계산하는 구조로 설계되었습니다. 두 방식을 혼용함에 따라 점수 집계 타이밍 불일치 문제가 발생할 수 있어, 감사 원장(SeasonScoreEventLog)을 통한 이중 검증 구조를 추가로 설계하여 해결하였습니다.

---

### 3-2. 지원 필요사항

현재 시점에서 자체적으로 해결 완료한 사항이 대부분이며, 별도의 외부 지원이 필요한 사항은 없습니다.

다만, 향후 플랫폼 사용자 규모가 확장될 경우 아래 사항에 대한 사업단 차원의 검토를 요청드릴 수 있습니다.

| 사항 | 내용 |
|------|------|
| GitHub API 추가 토큰 확보 | 사용자 수 증가 시 GitHub API 호출량 증가에 대비한 GitHub App 또는 추가 OAuth App 등록 필요 가능성 |
| 챌린지 항목 설계 자문 | 실제 오픈소스 기여 활동을 효과적으로 장려하는 챌린지 항목 선정에 대한 전문가 자문 필요 시 |

## 참고: 시스템 아키텍처 요약

```
[사용자]
  │
  ├─ 로그인 → 출석 점수 자동 지급 (비동기 이벤트)
  ├─ 게시글 작성 → 커뮤니티 점수 자동 지급 (비동기 이벤트)
  │
[수확기 (Harvester) - 매일 04:00]
  │
  ├─ GitHub GraphQL API → 커밋·PR·이슈·저장소 데이터 수집
  ├─ 커밋 점수 재계산 → SeasonRankingScore 업데이트
  ├─ 챌린지 평가 이벤트 발행 → RabbitMQ
  │       └─ Challenge-Service: 조건 평가 → 달성 시 점수 지급
  ├─ GitHub 전체 랭킹 점수 계산 (활동·다양성·영향력)
  └─ 전체 순위 및 티어 일괄 갱신

[관리자]
  └─ 프로젝트 종료 처리 → 참여자 프로젝트 점수 일괄 지급
```

## 참고: 랭킹 관련 API 목록 및 처리 절차

### API 1. 현재 시즌 전체 랭킹 조회

```
GET /v1/seasons/current/rankings
```

| 항목 | 내용 |
|------|------|
| 인증 | 불필요 (비로그인 공개) |
| Query | `page` (0-indexed, 기본 0), `size` (기본 50) |

**처리 절차**

1. `seasonRepository`에서 `is_active = true`인 현재 시즌 조회
2. `season_ranking_score` 테이블에서 해당 시즌의 전체 참여자를 `total_score DESC, rank_in_season ASC` 순으로 페이징 조회
3. 각 레코드를 `SeasonRankingEntryResponse`(순위·유저ID·이름·프로필이미지·총점·티어)로 변환
4. 시즌명·종료일·목록·페이징 정보를 묶어 응답

**응답 예시**

```json
{
  "seasonName": "2026-1학기",
  "endDate": "2026-06-30",
  "rankings": [
    { "rank": 1, "userId": 42, "userName": "홍길동", "profileImageUrl": "https://...", "totalScore": 87.35, "tier": "CHALLENGER" }
  ],
  "totalCount": 153,
  "page": 0,
  "size": 10
}
```

### API 3. 현재 시즌 내 랭킹 조회

```
GET /v1/seasons/current/rankings/me
```

| 항목 | 내용 |
|------|------|
| 인증 | 필요 (Bearer Token) |
| 응답 오류 | 401 (미인증), 404 (활성 시즌 없음 또는 점수 없음) |

**처리 절차**

1. JWT 토큰에서 로그인 유저 추출
2. 현재 활성 시즌 조회
3. `season_ranking_score`에서 해당 시즌·해당 유저의 레코드 조회
4. 순위·총점·티어·카테고리별 점수(출석·커밋·챌린지·프로젝트·커뮤니티) 반환

**응답 예시**

```json
{
  "seasonName": "2026-1학기",
  "endDate": "2026-06-30",
  "rank": 17,
  "totalScore": 43.25,
  "tier": "GOLD",
  "attendanceScore": 1.23,
  "commitScore": 12.50,
  "challengeScore": 8.40,
  "projectScore": 18.00,
  "communityScore": 3.00
}
```

### API 5. GitHub 전체 랭킹 조회

```
GET /v1/github/rankings
```

| 항목 | 내용 |
|------|------|
| 인증 | 불필요 |
| Query | `page` (0-indexed, 기본 0), `size` (기본 50) |

**처리 절차**

1. `github_user_statistics` 테이블에서 `total_score DESC` 순으로 페이징 조회
2. 각 통계 레코드에 매핑된 User 정보를 배치 조회 (N+1 방지)
3. 페이지 내 순위를 `(page * size) + index + 1`로 계산하여 부여
4. 각 항목을 순위·유저정보·총점·활동수준·다양성·영향력 점수로 변환하여 응답

**응답 예시**

```json
{
  "rankings": [
    {
      "rank": 1, "userId": 7, "userName": "김철수", "profileImageUrl": "https://...",
      "totalScore": 8.5, "activityScore": 3.0, "diversityScore": 1.0, "impactScore": 4.5
    }
  ],
  "totalCount": 89,
  "page": 0,
  "size": 10
}
```

---

### API 6. 내 GitHub 랭킹 조회

```
GET /v1/github/rankings/me
```

| 항목 | 내용 |
|------|------|
| 인증 | 필요 (Bearer Token) |
| 응답 오류 | 401 (미인증), 404 (GitHub 미연동 또는 통계 없음) |

**처리 절차**

1. JWT에서 로그인 유저 추출 → 연동된 GitHub 계정 확인
2. `github_user_statistics`에서 해당 유저 통계 조회
3. 전체 통계 테이블에서 내 점수보다 높은 유저 수를 카운트하여 내 순위 계산
4. 순위·총점·활동수준·다양성·영향력 점수 반환

**응답 예시**

```json
{
  "rank": 5,
  "totalScore": 7.0,
  "activityScore": 3.0,
  "diversityScore": 0.7,
  "impactScore": 3.3
}
```

### 점수 갱신 흐름 요약 (API와 연관된 내부 처리)

```
[실시간 점수 반영]
로그인        → UserLoginEvent 발행 → 출석 점수 즉시 지급 (비동기)
게시글 작성   → ArticleCreatedEvent 발행 → 커뮤니티 점수 즉시 지급 (비동기)

[배치 점수 반영 - 매일 04:00]
1. GitHub API 데이터 수집 (수확기)
2. 커밋 점수 재계산 (일별 cap 3건 × 0.05pt)
3. 챌린지 평가 이벤트 → RabbitMQ → Challenge-Service → 달성 시 점수 지급
4. GitHub 전체 랭킹 점수 계산 (활동·다양성·영향력)
5. 전체 순위 재계산 (동점자 공동 순위)
6. 티어 배정 (백분위 기반)

[관리자 처리]
프로젝트 종료 처리 → 참여자 프로젝트 점수 일괄 지급 (POST /v1/admin/seasons/projects/{id}/close)
```
